Rebuilding the HeavenCraft storefront

Replace a client-rendered Create React App site that search engines cannot read and customers cannot buy from, with a modern storefront that prerenders every product, takes real payments through Shopify, and serves over a certificate browsers actually trust.

00 — Summary

The short version

Found while surveying — fix regardless of what else we do

theheavencraft.in is serving a self-signed TLS certificate. Port 443 is open, but the certificate's issuer and subject are both CN=theheavencraft.in — the stock cPanel placeholder. Every visitor who reaches the site over https:// gets a full-page browser interstitial reading “Your connection is not private” before they see a single product.

This also hard-blocks the commerce plan: no payment provider will integrate against it, and a Shopify Buy Button or Storefront call from an untrusted-origin page is a dead end. Detail and evidence in §01, fix options in §03.

Update — fixed. The domain's nameservers have since been moved to Cloudflare and both records are proxied. Cloudflare now terminates TLS at the edge with its own free, auto-renewing certificate — verified live and browser-trusted as of 20 Sep 2026. This cost nothing and GoDaddy stays the origin host. Three settings remain to make it correct end-to-end; see §3.3.

What we are proposing

  1. Keep the brand, the photography and the catalog. 34 products, 197 image files and the gold-on-black identity all carry over. Nothing is re-shot and nothing is re-typed.
  2. Rebuild the front end on the stack already proven in the ergonomic-furniture-website prototype, but compiled to plain static HTML so it can be hosted anywhere — including the existing GoDaddy cPanel account.
  3. Hand commerce to Shopify. Cart, checkout, payment, PCI scope, order management and refunds become Shopify's problem rather than code we own and maintain.
  4. Fix HTTPS before anything else ships.
One correction to flag early

Shopify's free SSL covers a domain pointed at Shopify's own storefront. It does not issue a certificate for a site hosted somewhere else, so it will not fix the certificate on the GoDaddy box. That turned out not to matter — Cloudflare now provides the storefront certificate free, and Shopify's free SSL still covers the shop. checkout subdomain. Both are ₹0. Worked through in §03.

The reviews cannot ship as they stand

The catalog carries named, dated, five-star reviews flagged "verified": true. The project's own PRODUCT.md records these as placeholder content of unverified provenance. Publishing them is two separate problems, and the second is the serious one:

  • Showing invented testimonials attributed to named people is a consumer-protection exposure.
  • Emitting them as aggregateRating structured data is a search-policy breach that gets a storefront penalised — and it is exactly the kind of thing that surfaces long after launch.

The prototype already solves this correctly with two separate flags — one that renders the section as plainly-labelled sample content, and one that only a genuine review set unlocks. We carry that behaviour across unchanged. Same rule for the “10K+ Happy Customers” and “4.8★ Average Rating” figures: the real catalog is 34 products, and those numbers were confirmed aspirational.

The biggest single scope saving in this plan

The prototype's roadmap puts a bespoke admin portal — product CRUD, stock, image upload, enquiry inbox — in front of launch, on the principle that the owner must never need a developer to sell something. Shopify's admin already is that portal, built, maintained, and with a mobile app. Adopting Shopify does not just add payments; it deletes an entire build phase and the long tail of maintaining it.

What the Razorpay scaffolding is worth to us

Honestly: very little. src/lib/payments/types.ts models a gateway that creates an order server-side and verifies a signature on the way back. Shopify's model is the opposite — the browser builds a cart and is redirected to Shopify's own hosted checkout, and we never handle a payment credential at all. That interface does not adapt; it gets removed. The feature-flag discipline around it is worth keeping.

03 — Hosting

Can GoDaddy cPanel run this?

Decision taken

Hosting stays on GoDaddy. Commerce runs on Shopify's APIs. Everything below is written to that decision. Where it costs us something, that is stated plainly rather than smoothed over.

3.1  The concern is correct

A GoDaddy shared cPanel plan is not a place to run Next.js in its normal server mode. Server-side rendering needs a long-lived Node process, and even where cPanel exposes a Node.js application manager, running a framework server behind Passenger on shared hosting is fragile, memory-capped and unsupported by GoDaddy when it breaks. We should not plan around it.

Now confirmed against primary sources — SSR is not merely unwise here, it is unavailable
  • The feature is provider-gated, not user-gated. cPanel's Application Manager runs Node under Phusion Passenger, and cPanel's own docs tell end users: “If you need this feature, contact your hosting provider.” The familiar “Setup Node.js App” icon is CloudLinux's Node.js Selector, installed by root.
  • This account has no route to enabling it. WHM ports 2086/2087 are closed — no root, no Feature Manager. The only lever is a GoDaddy support ticket.
  • Even if enabled, it is hostile to modern Next.js. CloudLinux documents that “Phusion Passenger cannot load ECMAScript modules and can only load CommonJS modules” — and Next.js is ESM-first. Memory ceilings are fixable only in WHM, and there is no port binding and no process manager.
  • GoDaddy documents Node.js only for VPS and dedicated servers. The archived shared-hosting plan page lists Economy through Maximum with zero Node.js mentions.

This is a good outcome rather than a constraint to mourn: it forces the static export, and the static export is faster, cheaper and more reliable than SSR would have been for a 34-product catalog that changes rarely.

3.2  But we do not need a server

Next.js has a build mode — output: 'export' — that emits one plain HTML file per route plus static CSS and JS, and nothing else. Quoting the Next.js 16 documentation directly:

// next.config.ts
const nextConfig = {
  output: 'export',        // emit static HTML/CSS/JS -- no Node server
  trailingSlash: true,     // /chairs/ -> /chairs/index.html, which Apache serves natively
  images: { unoptimized: true },
}

“Since Next.js supports this static export, it can be deployed and hosted on any web server that can serve HTML/CSS/JS static assets.” Apache on cPanel is exactly that. Server Components still run — they execute at build time, on our machine or in GitHub Actions — so the 34 product pages are rendered into real HTML with real content, then uploaded.

What this buys us, on the hosting we already pay for
  • The SEO problem is solved. Every product page ships as complete HTML with its own title, description and structured data — versus today's 1,126-byte empty shell.
  • The deployment pipeline does not change. The existing GitHub Actions workflow keeps working; only local-dir changes from build/ to out/.
  • No new hosting bill, no server to patch, no database to run or back up.
  • Nothing can go down at 2am. Static files on Apache have no runtime to crash.

The .htaccess must change — this will break the site if missed

The current rule rewrites every request to /index.html, because a CRA SPA has only one HTML file. A static export has real files at real paths. Keeping the catch-all would serve the homepage at every URL and silently destroy the entire SEO gain we are doing this for.

The replacement serves real files, falls back to a real 404.html, and adds long-lived cache headers for fingerprinted /_next/static assets. Research turned up a real Next.js issue report where leaving a CRA-style catch-all in place against a static export produced HTTP 500s, not just wrong content — so this is a hard blocker, not a tidy-up.

# public/.htaccess — static export. REPLACES the CRA catch-all.

<IfModule mod_rewrite.c>
  RewriteEngine On
  RewriteBase /

  # --- Canonical host. Enable the HTTPS rule ONLY after §3.3 is done. ---
  # RewriteCond %{HTTPS} !=on
  # RewriteRule ^ https://%{HTTP_HOST}%{REQUEST_URI} [L,R=301]

  RewriteCond %{HTTP_HOST} ^theheavencraft\.in$ [NC]
  RewriteRule ^ https://www.theheavencraft.in%{REQUEST_URI} [L,R=301]

  # Real file or real directory → serve it, untouched.
  RewriteCond %{REQUEST_FILENAME} -f [OR]
  RewriteCond %{REQUEST_FILENAME} -d
  RewriteRule ^ - [L]

  # /chairs → /chairs/index.html   (matches trailingSlash: true)
  RewriteCond %{REQUEST_FILENAME}/index.html -f
  RewriteRule ^(.*)$ /$1/index.html [L]

  # /chairs → /chairs.html         (belt and braces)
  RewriteCond %{REQUEST_FILENAME}\.html -f
  RewriteRule ^(.*)$ /$1.html [L]
</IfModule>

# A real 404 — not the homepage wearing a 200.
ErrorDocument 404 /404.html

<IfModule mod_headers.c>
  # /_next/static/** is content-hashed by the build: safe to cache forever.
  SetEnvIf Request_URI "^/_next/static/" IMMUTABLE_ASSET
  Header set Cache-Control "public, max-age=31536000, immutable" env=IMMUTABLE_ASSET

  # HTML must revalidate, or a rebuild stays invisible for a week.
  <FilesMatch "\.html$">
    Header set Cache-Control "public, max-age=0, must-revalidate"
  </FilesMatch>

  Header always set X-Content-Type-Options "nosniff"
  Header always set Referrer-Policy "strict-origin-when-cross-origin"
</IfModule>

<IfModule mod_deflate.c>
  AddOutputFilterByType DEFLATE text/html text/css application/javascript \
                                application/json image/svg+xml
</IfModule>
Sequencing trap: do not force HTTPS before the certificate is valid

The RewriteCond %{HTTPS} !=on redirect is deliberately commented out above. Switching it on while the certificate is still self-signed would push every visitor into the browser interstitial with no working HTTP fallback — turning a bad first impression into a completely unreachable site. It gets uncommented in §3.3, as the last step, once a valid certificate is confirmed live.

3.3  Fixing HTTPS — solved, at ₹0, by Cloudflare

Status change — verified live, 20 Sep 2026

The domain's nameservers have been moved to Cloudflare (salvador.ns.cloudflare.com, maeve.ns.cloudflare.com) and both @ and www are proxied through Cloudflare's edge. This removes the certificate problem entirely and costs nothing.

Cloudflare terminates TLS at the edge with its own free, auto-renewing certificate, so the visitor never sees GoDaddy's self-signed one. As a side effect the site also gains a global CDN, Brotli compression and HTTP/3, none of which were on the table before.

The three settings that matter, in order

#SettingValueWhy
1 SSL/TLS → Overview → encryption mode Full Not Flexible sends traffic to GoDaddy unencrypted and causes redirect loops. Not Full (strict) — it validates the origin certificate, and GoDaddy's is self-signed, so the site would break with error 526. Full encrypts to the origin without validating it: correct for today.
2 SSL/TLS → Origin Server → Create Certificate Install into cPanel A free Cloudflare Origin CA certificate, valid 15 years. Paste it into cPanel → SSL/TLS → Install an SSL Website. This replaces GoDaddy's self-signed cert on the origin and means AutoSSL is never needed — which sidesteps the whole question of what the GoDaddy plan does or doesn't include.
3 Encryption mode, after step 2 Full (strict) Once the origin holds a real certificate, tighten it. This closes the gap where anyone between Cloudflare and GoDaddy could impersonate the origin. The proper end state.
Redirect-loop trap — pick one place to force HTTPS, not two

Turn on Cloudflare → SSL/TLS → Edge Certificates → Always Use HTTPS, and leave the RewriteCond %{HTTPS} !=on block in .htaccess commented out. If Cloudflare is in Flexible mode and Apache also forces HTTPS, the two bounce the request back and forth until the browser gives up with ERR_TOO_MANY_REDIRECTS. Cloudflare owns this redirect now. The same applies to the apex→www rule, which is better expressed as a Cloudflare Redirect Rule than in .htaccess.

Test the .htaccess on a staging subfolder first

Next.js publishes no official Apache configuration — only an nginx example — so the block in §3.2 is a construction, not a vendor-blessed file. On a restrictive AllowOverride policy some directives can return a 500 rather than being ignored. Deploy it to a staging path and confirm before it touches the live document root. This is Phase 1 work in §10, deliberately sequenced before anything customer-facing.

What this changes elsewhere in the plan

  • Shopify product-image import is unblocked once the certificate issues — Shopify fetches images over HTTPS from publicly reachable URLs, which was previously impossible.
  • Caching moves to the edge. The Cache-Control headers in §3.2 are still the source of truth; Cloudflare honours them, so fingerprinted /_next/static assets get cached globally rather than just in the visitor's browser.
  • Purge on deploy. Add a Cloudflare cache-purge step to the GitHub Actions workflow after the FTP upload, so a rebuild is visible immediately instead of waiting out the edge TTL.
  • GoDaddy's origin IP is now hidden behind Cloudflare, which is a genuine security improvement on shared hosting.

3.4  The honest cost of no server: publishing

With no database and no ISR, the catalog is baked in at build time. Changing a price means a rebuild and redeploy — roughly two to three minutes, triggered by a commit. That is acceptable precisely because, as you noted, inventory changes here are rare.

It stops being acceptable the moment the owner wants to change a price from his phone on a Sunday. Two ways to buy that back when it matters, neither needed at launch:

  • Fetch prices in the browser at page load from Shopify's tokenless Storefront API, so the static HTML carries a build-time price for crawlers and the live Shopify price refreshes on view. Removes the rebuild for price changes entirely.
  • Trigger the build from Shopify. A Shopify webhook on product update calls a GitHub Actions repository_dispatch, which rebuilds and re-uploads. Fully automatic, about half a day's work.
04 — Commerce

What Shopify is actually for

Shopify is not being adopted as a website. It is being adopted as the part of an e-commerce business that is genuinely hard to build and dangerous to get wrong: taking money, holding card data, and keeping a record of what was sold.

4.1  The division of labour

Our static site owns

Design, photography, copy, navigation, category and product pages, SEO and structured data, the cart UI, performance.

Shopify owns

Prices of record, cart state, checkout, payment, PCI compliance, orders, refunds, customer records, tax configuration, and the admin the owner logs into.

4.2  This works without a server — confirmed

This was the load-bearing question for the whole plan, so it was verified against Shopify's own documentation rather than assumed. As of API version 2026-07, the Storefront API supports tokenless access:

Shopify, docs for Storefront API 2026-07

“Tokenless access allows API queries without an access token providing access to essential features such as: Products and Collections · Selling Plans · Search · Pages, Blogs, and Articles · Cart (read/write).”

Products, collections, search and full cart read/write — the entire surface this storefront needs — with no token and no backend.

The auth model, in full

The useful framing is that for this architecture the authentication problem does not get solved, it disappears. There is no secret anywhere in the runtime path, so there is nothing to leak from static files.

What the site needs to doAuthRuns where
Read products, variants, live pricesNone tokenlessBrowser
Read collectionsNone tokenlessBrowser
SearchNone tokenlessBrowser
Create cart, add / update / remove linesNone tokenlessBrowser
Get cart.checkoutUrlNone tokenlessBrowser
Take paymentNot oursShopify's hosted checkout
Metafields, product tags, menus, customer accountsPublic token designed to be publishedBrowser
Create products, CSV import, draft ordersAdmin secretNever the browser — Shopify admin UI, or GitHub Actions with the secret in GitHub Secrets

Only the last row involves a real secret, and nothing in that row happens at runtime. Catalog changes are an admin activity, not a customer activity — so the secret never needs to exist in anything we deploy.

If we ever do need a token

Should we later want product tags or metafields, a public access token covers it. Shopify's own description is unambiguous — it is “used to query the API from a browser or mobile app, where the token is visible to buyers”, sent in the X-Shopify-Storefront-Access-Token header. It is designed to be published. Its counterpart, the private token, is the one Shopify says “should be treated as secret and not used on the client-side” — we simply never create one.

CORS — verified empirically, not just read in a doc

The remaining practical question is whether a browser on our own domain is actually allowed to call Shopify. A live preflight was sent from our exact origin:

OPTIONS https://{shop}.myshopify.com/api/2026-07/graphql.json
Origin: https://theheavencraft.in
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type,x-shopify-storefront-access-token

→ access-control-allow-origin: *
→ access-control-allow-methods: POST
→ access-control-allow-headers: … X-Shopify-Storefront-Access-Token …

follow-up POST → HTTP 200 with GraphQL data

Browser fetch() from an arbitrary static origin works with no proxy and no server. This was tested against a live Shopify storefront rather than inferred from documentation.

Rate limiting — the thing that replaces auth

Because there is no token, Shopify meters tokenless and public access by the buyer's IP address, and caps tokenless queries at 1,000 complexity points. Two practical consequences:

  • Capacity scales with real buyers, which is exactly the shape of our traffic. One visitor cannot consume another's budget.
  • Queries must stay lean — request only the fields actually rendered. A greedy nested query can breach 1,000 points on its own and fail in production while passing in testing.

The checkout handoff

cartCreate            → returns a cart id
cartLinesAdd          → add { merchandiseId: variantId, quantity }
query cart.checkoutUrl
window.location = checkoutUrl   → Shopify's hosted checkout

From that redirect onward, Shopify runs everything. We never touch a card number, which is what keeps PCI scope off this project entirely.

Three implementation rules that are easy to get wrong
  • The cart ID contains a secret. It has the form <token>?key=<secret>, and Shopify's guidance is explicit: “Never expose the secret part of the ID. Treat it like a password — don't include it in shareable links, public pages, or any client-side code.” Storing it in the buyer's own localStorage is fine; putting it in a URL, a share link or server-rendered markup is not. This rules out “share your cart” links.
  • Shopify's price is the price of record. CartCost is documented as “estimated … subject to change”, with checkout final. Cart and checkout totals must be rendered from cart.cost, never recomputed from our JSON — otherwise we will one day display one number and charge another.
  • The API is versioned four times a year. Pin 2026-07 explicitly and diarise a review, or the storefront breaks on a schedule nobody is watching.

4.3  Payments in India — the part that costs real money

Shopify Payments is not available in India

India is absent from Shopify's supported-countries list, so an Indian merchant must use a third-party gateway — and Shopify charges its own transaction fee on top of the gateway's. Every Shopify fee waiver is conditioned on using Shopify Payments, so none of them apply here.

ComponentBasic planNote
Razorpay MDR2.00%Cards, netbanking, wallets, UPI alike
GST on that fee0.36%18% on the 2%
Shopify third-party fee2.00%1.0% on Grow, 0.6% on Advanced
All-in, prepaid order≈ 4.36%≈ ₹785 on a ₹17,999 chair

Upgrading Basic → Grow trades ₹4,100/month for 1% of turnover, so it only pays back above roughly ₹4.1 lakh/month in prepaid volume. Stay on Basic.

UPI is not free, which is a common and expensive assumption. RBI mandates zero MDR on UPI, but Razorpay applies its 2% as a platform fee regardless. Note too that in Shopify's India checkout only card payments are truly on-site; UPI, netbanking and wallets redirect to the gateway and back.

Get this in writing before committing — it is the biggest single unknown

Shopify's own help pages contradict each other on whether Cash on Delivery orders attract the 2% third-party fee when Shopify Payments is unavailable. One page waives the fee for manual payment methods, but only in a sentence conditioned on using Shopify Payments. Another states the fee applies to “all orders that go through Shopify's checkout system.”

For a furniture business where COD is likely to be a large share of orders, this is the dominant variable cost — roughly ₹360 of fees on a ₹17,999 COD table with no gateway involved. Ask Shopify India support verbatim: “My store is in India and Shopify Payments is unavailable to me. Do I pay the third-party transaction fee on orders placed using the manual Cash on Delivery payment method?”

4.4  Two things Shopify will not do for you

  • GST-compliant invoices. Shopify's answer is unusually blunt — “Does Shopify provide a GST-compliant bill? No.” It also cannot split CGST/SGST into separate invoice lines. A GST invoicing app (~₹450/month) is mandatory, not optional, and belongs in the budget from day one. India tax defaults also ship hard-coded to Karnataka as the home state and must be reconfigured.
  • Sane furniture freight. Indian couriers bill on volumetric weight (L×W×H ÷ 5000) and charge the greater of actual and volumetric — an assembled chair can bill as ~68 kg. The existing ₹20,000 free-shipping threshold was inherited from the old site and has never been tested against real rates. Price actual SKUs in Shiprocket's calculator before that promise goes back on the page.

The two catalogs are joined on a stable key — the legacy product ID written into a Shopify metafield or SKU — so the build can fail loudly if a product exists on one side and not the other. 5.2  The alternative we are consciously not taking

Recorded so the trade-off is deliberate, not accidental

Independent research on this stack came back recommending the opposite: put the whole site on a Shopify theme, retire GoDaddy hosting, and skip the custom front end. The argument is worth stating fairly:

  • It fixes HTTPS by itself, with no certificate work at all. Moot Cloudflare has since fixed HTTPS for free — see §3.3. This argument no longer carries weight.
  • The owner could change layout, banners and content himself, not just product fields. With a custom front end, every visual change is a developer task.
  • At 34 products, a modern Shopify theme's performance and SEO are unlikely to be the bottleneck, and platform guardrails come free.
  • It is cheaper: no build-and-deploy pipeline to maintain.

Against that, a theme cannot reproduce the gold-on-black design in §08 without significant theme development, the brand ends up looking like other Shopify stores, and the existing React codebase and photography pipeline are discarded. You have chosen the custom front end on GoDaddy, and this plan executes that — but the honest summary is that we are buying design control and paying for it in owner self-service. If the owner later wants to restyle pages himself, that decision gets revisited, and the Shopify catalog built in Phase 2 means nothing is wasted if it does.

07 — Data

Catalog & data

7.1  Getting 34 products into Shopify

A real Product and ProductVariant must exist in Shopify for every purchasable item — the cart API is variant-bound and will not accept an arbitrary line item. There is no way around this, and at 34 SKUs it is about an hour of work via native CSV import.

  • Export a CSV from the store first and match its exact header row. Shopify's own docs disagree on whether the image column is Image Src or Product image URL.
  • Images must be at publicly reachable URLs for Shopify to pull and re-host them. Convenient here: they are already live on the current site — but that site's certificate is untrusted, so fix TLS first or the import may fail. A neat forcing function.
  • Additional images are extra rows carrying only the handle and image URL.
  • Leave inventory untracked. Tracking causes checkout to block at zero stock, which is wrong for a reseller ordering in on demand.
  • Put 6-digit HSN codes in the HS tariff field during import — backfilling later across the catalog is far more expensive than entering it once.
  • Trim the 7 leading-space product names before export, or they import with the space and corrupt every generated handle.

7.2  Draft orders as a side channel, not the main road

Custom line items that do not exist in the catalog are possible — via Admin API draft orders — but that needs a server-side secret and would destroy the tokenless, serverless architecture this plan depends on. It stays in the back pocket for genuine one-offs: custom-dimension tables and bulk office quotes, agreed by email and invoiced through Shopify. That is what draft orders are designed for.

8.2  Type

Archivo alone, varied by its real width axis rather than by bringing in a second typeface to shout. 8.3  Rules the build holds to

One gold action per view

Gold is the primary action and appears once. Everything else is an outline that warms to gold on hover, so the page never has two things competing to be pressed.

Hairlines, not boxes

Structure is separated by a 1px gold gradient rule that fades to transparent, rather than by stacking bordered panels.

Real depth only

Shadows carry an offset and a soft blur. Never a zero-offset halo, which reads as a glow rather than as light.

One authored motion moment

The hero settles into place as if a light came up on it. Everything else is a hover or a page change, and all of it collapses under prefers-reduced-motion.

Photography under an angled scrim

Raked from the left on desktop so the product keeps its own light; lifted from the bottom on a phone, where there is no room beside it.

Never invent proof

An empty testimonial section beats a fabricated one. Counts and prices are read from the catalog, never written into copy, so a range the owner empties disappears instead of lying.

Two photographs are legally unusable at hero size

The prototype's audit found supplier imagery with text and third-party branding baked into the pixels. This carries into our build as a hard denylist:

  • tables/gaming-desk/1 - Quantum.jpeg — carries the supplier's own brand name, “Eureka Ergonomic”, burned into the desk leg. Selling that under the HeavenCraft name with a supplier's mark visible is a trademark exposure, not a taste question.
  • tables/height-adjustable-table/6 - Movix6.jpeg — marketing overlay text (“BUILT FOR FOCUS…”, “WEIGHT CAPACITY”, “FRONT VIEW”) baked in.

Both stay available on their own product pages, where they plainly read as supplier shots. Neither is ever used full-bleed. Gaming desks need re-shot or supplier-cleared photography before they can be merchandised prominently — worth starting now, since it is the one item on this plan with a lead time we do not control.

Indian payment gateways require published shipping, returns/refund, privacy and terms pages as a condition of activation, and the merchant review will check they exist and are reachable. These need writing — they are content, not code, and they are on the critical path to accepting a first payment. Worth drafting early.

9.2  Sub-category pages are the main SEO opportunity

The catalog already carries a clean two-level taxonomy that the current site renders as nothing more than a filter chip. Promoting sub-categories to real, indexable URLs turns 3 thin category pages into 16 targeted landing pages — “height adjustable table”, “mesh chair”, “executive table” — which is what people actually search for. That costs almost nothing to build once the data is normalised, and it is where organic traffic will come from.

9.3  Redirect map

All 34 legacy product URLs get a permanent redirect to their new slug, plus the group routes. Even with little index presence, anything shared over WhatsApp or linked from a marketplace listing keeps working.

/product/chair-mesh-004          → /chairs/neuro-mesh-chair
/product/table-executive-003     → /tables/imperium-executive-table
/product/accessories-footrest-002 → /accessories/footrest-plus
… 34 rules generated from products.json, not hand-written

The map is generated from products.json at build time so it cannot drift, and it is emitted in whichever form the final host needs — Apache .htaccess rules or a platform redirects file. The 7 leading-space product names must be trimmed before slugs are generated, or those seven URLs start life malformed.

9.4  Per-page SEO, which the site has none of today

  • Unique <title> and meta description per product and per category, generated from the catalog
  • Product structured data with offers, price, INR and availability — without aggregateRating until reviews are genuine
  • BreadcrumbList structured data, and Organization on the homepage
  • sitemap.xml and robots.txt generated at build
  • Canonical URLs, Open Graph and Twitter cards so WhatsApp shares render a product image
  • Indexing gated on the real domain, so test deploys can never be indexed and go live automatically at cutover

9.5  Brand identity in the browser chrome — currently the React logo

Verified live today, not inherited from the audit

The site is serving Create React App's stock branding, untouched:

GET /favicon.ico    → 200  image/x-icon   3,870 b   ← React atom
GET /logo192.png    → 200  image/png      5,347 b   ← React atom
GET /manifest.json  → 200  application/json 492 b

  { "short_name": "React App",
    "name": "Create React App Sample",
    "theme_color": "#000000",
    "background_color": "#ffffff" }

Three surfaces are affected: the browser tab, the Google search result, and the Android home-screen install, which currently creates an app called “React App”.

Google's rules, and the three that actually bite

Google supports rel="icon", apple-touch-icon and apple-touch-icon-precomposed, requires a square image of at least 8×8 and recommends larger than 48×48, and needs Googlebot-Image to be able to crawl it. Our robots.txt is fully permissive, so nothing is blocked. The subtle constraints:

  • One favicon per hostname. Google treats theheavencraft.in and www.theheavencraft.in as different sites. This is another reason the canonical host must be settled and redirected — see §3.2.
  • The URL must be stable. Do not let the build fingerprint the favicon path. Keep it at a fixed /favicon.ico in public/ with an explicit <link>, rather than relying on a framework convention that may append a content hash.
  • Recrawl takes days to weeks. Google's words. So this ships in Phase 0, not at launch — the sooner the clock starts, the sooner search results stop showing a React logo. Follow it with a URL Inspection → Request Indexing on the home page.

A design constraint worth catching early

The existing logo — a gold HC monogram inside a gold ring, with “HeavenCraft” arced around the top — is already square and works beautifully as a mark. But the arced wordmark becomes an illegible smudge below about 64 px. The favicon should therefore be the monogram and ring only, with the wordmark dropped. Same identity, drawn for the size it will actually be seen at.

Like the certificate, the icons and manifest can be fixed on the current CRA site this week — they are static files in public/. There is no reason to make this wait on the Next.js work, and given Google's multi-week recrawl window, there is a real reason not to.

11 — Cutover

Launch runbook

This cutover is unusually low-risk, for one reason established in §1.1: there are no MX records, so no mailbox can break. We are also not moving hosts or nameservers — only replacing files in the same document root, and adding one subdomain.

A day before

  • Lower DNS TTL on the shop record to 600s so a rollback takes ten minutes
  • Take a full FTP backup of the current document root — this is the rollback
  • Confirm the staging build renders correctly on the real host, not just locally

Cutover

  1. Add shop CNAME → shops.myshopify.com. (trailing dot) in GoDaddy DNS
  2. Connect shop.theheavencraft.in in Shopify admin; wait for its certificate — up to 48h, so do this step days early
  3. Deploy the static export over the existing root; verify the new .htaccess landed
  4. Spot-check: homepage, one product per group, a sub-category page, a deliberate 404
  5. Verify 301s: request 5 old /product/<id> URLs, confirm they land correctly
  6. Place one real end-to-end order — add to cart, checkout, pay, confirm it appears in Shopify admin and the GST invoice generates
  7. Confirm HTTPS is valid and HTTP redirects to it
  8. Submit sitemap.xml in Google Search Console

After

  • Watch Search Console coverage for a fortnight — the index will churn as URLs change
  • Restore TTLs
  • Keep the old build in the backup for a month before deleting
Rollback

Re-upload the backed-up build/ and the old .htaccess. Because DNS does not change for the storefront, rollback is an FTP restore measured in minutes, with no propagation wait.
